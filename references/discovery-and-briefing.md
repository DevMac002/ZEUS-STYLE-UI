# Discovery and briefing

## Minimum brief

Establish, as far as available:
- Product/site type and business or user goal.
- Primary audience and their key needs.
- Primary user action and supporting journeys.
- Content and required pages/components.
- Brand, references, assets, and existing design system.
- Technical stack and constraints.
- Accessibility, localization, performance, SEO, and integration requirements.
- Definition of done.

## Question discipline

Ask only questions that materially affect the outcome. Batch related questions in one message. If missing details are low risk, state an assumption and proceed. Do not ask for information already present in the prompt or repository.

## Inspecting a repository

Use available file tools to inspect package manifests, routes, key components, CSS/styling setup, tokens, tests, and recent working-tree changes. Avoid dumping the entire repository into context. Follow relevant imports and conventions.

## Task classification

- New project: discover, propose concept(s), approve, specify, implement.
- Existing project: inspect first, preserve patterns, propose focused changes.
- Redesign: audit existing experience, distinguish retained constraints from intended changes, propose direction.
- Component-only: minimize discovery and deliver within the component's scope.
- Audit-only: do not edit unless asked.
